System architecture

Factory Inventory Management System

A two-process demo app. A Vue single-page app in the browser talks over plain HTTP to a single-file FastAPI service, which serves and filters JSON fixtures held in memory. There is no database, no auth, and no build step between them.

How the pieces connect

Every request follows the same path. The only shared state on the client is the filter singleton; the only state on the server is the fixture lists loaded at startup.

Vue client FastAPI server JSON fixtures Dashed: not on the request path

Data flow: one filter change, end to end

What happens when someone picks “Tokyo” in the warehouse dropdown while on the Dashboard. The order matters, which is why the steps are numbered.

  1. FilterBar writes the shared ref

    FilterBar.vue is bound with v-model to selectedLocation, a ref declared at module scope in useFilters.js. Because the ref lives outside the function, every component that calls useFilters() receives the same instance.

  2. The view's watcher fires

    Each view watches only the filters it cares about. Dashboard and Orders watch all four; Inventory, Demand and Backlog watch location and category; Spending watches period alone. The watcher calls the view's load function.

  3. UI filters become API params

    getCurrentFilters() renames period to month and passes the rest through. api.js then drops any value equal to "all" and builds the query string, so a cleared filter sends nothing at all.

  4. FastAPI filters in memory

    apply_filters() does an exact match on warehouse and case-insensitive matches on category and status. filter_by_month() does a substring match on order_date, expanding quarter keys like Q3-2025 into their three months. Nothing is indexed; every request is a linear scan of the fixture list.

  5. Pydantic shapes the response

    Routes declare a response_model, so the JSON going out contains exactly the model's fields. A key added to a fixture file is silently dropped until the matching model gains it.

  6. The view derives everything else

    Raw arrays land in refs such as allOrders and inventoryItems. Status counts, on-time delivery rate, category totals and the revenue-goal comparison are all computed properties, so the template re-renders without any further fetch. Currency formatting happens last, converting stored USD to JPY when the locale is Japanese.

Which filters reach which data

Inventory, demand and backlog have no time dimension, so the period filter does not touch them. The reports endpoints ignore filters entirely and aggregate the whole year.

Loose ends worth knowing before you change anything

None of these break the demo today, but each one will surprise you the first time you touch the area.

Client calls routes the server never defines

api.js has methods for /api/tasks and /api/purchase-orders. The backend imports a CreatePurchaseOrderRequest model but exposes neither route, so the Tasks modal shows only mock tasks and logs a fetch error.

Reports.vue bypasses the API client

It calls axios directly with the hard-coded URL instead of going through api.js, so any change to the base URL has to be made in two places.

The data generator does not match the data

generate_data.py writes orders from a catalog of Widgets, Bearings and Motors. The fixtures use Circuit Boards, Sensors and friends. Running it would break every category filter.

Test docs are stale

The tests README documents cd tests && uv run pytest, which fails because no pyproject lives there. Run cd server && uv run pytest ../tests instead. It also lists a test_orders.py that does not exist.

Quarters are pinned to 2025

QUARTER_MAP and the reports aggregation both hard-code 2025 month strings. Data from any other year silently falls out of quarter and report views.

Two locale files, one fallback

A missing Japanese key falls back to English, then to the raw key. New UI strings need entries in both en.js and ja.js, and product, customer and warehouse names are translated by helper functions, not by the dictionaries.
